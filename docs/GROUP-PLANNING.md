# WP8 group preferences and feasible planning

Open the board switcher → **Group preferences**. Declare households and K3/K5 options, collect independent rank/stamp responses, explicitly export a household JSON/ZIP, then open **Organizer summary**. Import returned files and resolve unfamiliar household labels yourself. Labels and SHA-256 identities are not authentication. A same-revision conflict never chooses an arrival-time winner; request a higher revision. The summary separates current, partial, pending, conflicting, unresolved and stale replies, points, stamps and explicitly shared concerns.

The local response export cache lives in the existing trip clock, outside Undo. Unchanged exports reuse their envelope; changed content advances the highest known revision, including after Undo. Concurrent exports are fenced so distinct file identities cannot reuse a revision. Personal native ZIPs preserve the cache, accepted ledger/history, planning facts and policy; shared guide/stay/selected copies omit them, including the encoded document. Native import and app reopen validate response hashes before attaching the writable store. Failed or stale imports retain the previous valid ledger. Async cryptographic validation produces a short-lived, person-only, document/revision-bound commit receipt; arbitrary JSON cannot bypass the command boundary.

**Planning facts and time slots** is optional. Opening or editing an ordinary card does not invoke the planner. Enter explicit local time blocks, dated sources, currency, whole-group budget/costs, duration, opening windows, reservation status, household attendance/availability/access and travel/rest buffers. Blank values stay unknown. Confirmed/inferred/unknown facts retain source/date and optional expiry; expired evidence cannot verify a future activity. A `source_date` is compared with the calendar date written in `as_of`'s own offset, so a fact dated after that local day stays tentative. Opening hours never establish reservation availability. Confirmed costs use currency minor units for exact budget comparisons; there is no exchange-rate inference.

The checker rejects known participant overlaps, closed venues, inaccessible activities, unavailable reservations, excessive duration/cost and insufficient confirmed travel/rest buffers. Meal/rest/fixed-booking commitments are preserved; a fixed-booked activity cannot be scheduled again in another slot, and a booked participant without access evidence keeps the result tentative. AND, at-most-one OR, required exactly-one, before and only-if rules are explicit. A partial search does not prematurely reject a dependency that may be filled later; final proposals enforce it. Denied households cannot be included in an assumed joint outing. A smaller party requires explicit, confirmed split permission, feasible supervision and transport; the checker never invents those. Missing essential facts make a result tentative. Booking status is a person-recorded marker, not a purchase action; held/confirmed card starts must agree with their protected time windows and are never moved by these proposals.

The default stored policy is `mot-group-planning` v1: hard feasibility, households receiving a known top-two choice, households receiving a first choice, participating rank points, then travel. It compares criteria lexicographically rather than adding minutes and points. The organizer can explicitly select the supported points-first order; the visible stored criteria change with it. Fairness counts only explicitly participating households with current confirmed attendance, access and availability; repeated activities do not receive duplicate credit. Availability windows are joined the same way for credit as for feasibility, so adjacent windows covering a slot count. Pending/partial knowledge and unknown acceptability remain visible.

Search is a deterministic beam of at most 32 states with one-option local swaps, bounded at 6000 candidate evaluations. Large problems narrow the beam (and the number of swap bases) so every slot is reached within the bound; the reported heuristic states the width used. If the bound is still reached, the result sets `search_bound_reached` and says so, and omissions read “not fully compared” rather than claiming a fairness loss. Full ties after the policy criteria prefer more scheduled activities, then verified-feasible over tentative, then stable IDs. It is a heuristic, not proof of a global optimum. Results include objective values, equivalent/alternative option sets, omissions and reasons. The four-household fixture gives the 36-point Beach/Boat/Garden/Cooking set four first choices, ahead of the 43-point set with three under the default policy; explicit points-first reverses that choice. Six-slot and inaccessible-boat cases are covered by tests.

**Propose a plan** performs no board write. Select the actual shared-card date changes you want. Apply rechecks selected dependencies/feasibility and the board revision, together with unselected planning activities that stay dated on the board at a declared slot start; a tentative choice requires explicit acknowledgment. One existing proposal Undo reverses the applied group changes while retaining unrelated/private/source data. Date/time conversion uses the destination IANA time zone and refuses repeated or nonexistent local clock times rather than choosing a DST offset. Data changed during preparation or after review requires a fresh proposal. Save is reported only after the existing durable-write fence succeeds. A storage failure reports “in this tab only”; **Download personal backup** produces a real native recovery ZIP without invoking PDF export.

**Booking attention** records a deadline independently from the activity start and never changes preferences or schedule dates. A verified deadline within 24 hours is urgent; importance is an explicit separate choice. A promotion can be urgent but optional, while a valued later activity can be important without urgency. Missing/stale deadlines stay unknown and passed deadlines remain identified. Tasks are private and undated as activities; Today displays them separately with source/date and cost certainty. Marking attention complete does not buy, cancel or pay.

The read-only tools accept explicitly supplied data and never read private board context:

```js
await window.motTrip.planGroup({configuration, ledger, planning, policy});
await window.motTrip.checkGroupPlan({configuration, ledger, planning, assignments});
await window.motTrip.call('trip_booking_attention', {attention, as_of});
```

The existing `tallyPreferences`/`trip_preference_tally` surface remains. Person-only commands handle planning configuration, response commits and attention-task creation; the usual board command/proposal paths handle authorized dates and Undo. No provider, booking or payment call is made. WP9 routing and its separate integration/review remain outside this WP8 change.

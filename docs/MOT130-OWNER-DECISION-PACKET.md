## Ten recommended decisions

| ID | Recommended owner choice |
| --- | --- |
| **T1 — boundary** | Select **A: one trusted typed-command room service** with fresh per-entity shared records. The service derives authenticated identity and validates current membership, role, household assignment, schema, limits and preconditions before every accepted transition. Clients cannot write room records or media references directly. **Reject raw Yjs updates as an authorization boundary.** Do not select a Firebase database or claim its rules/transaction capabilities proved yet. |
| **T2 — roles** | One owner manages invitations, revocation, household assignments, rounds, publication/scope changes, deletion and official room export. Editors edit existing ordinary shared cards/geometry and replace their media; they cannot publish local private content, administer members, change scope, delete, export through the room export action, or see other households' replies. Viewers read shared cards/media only. Household respondents read ordinary shared cards/media and read/write only their assigned household response. Owner may read all responses for coordination, but **may submit only for their own assigned household**. All other permissions deny by default. Unauthenticated, revoked and external-agent identities have no room read/write authority. No agent credentials or delegated administrator role in this slice. |
| **T3 — invitations** | Owner creates a **single-use, 24-hour, 256-bit random** room/role-bound invite; store only its digest. Put the secret in a URL fragment, remove it from the address before ordinary navigation, and submit it in a redacted HTTPS request body. No tokens in logs, analytics, referrers or exports. Redemption by an authenticated account creates a pending claim, **not membership or room-content access**. Owner verifies the intended person out of band and explicitly approves the immutable authenticated subject shown for that claim. Acceptance, expiry, use count and revocation must be atomic. No multi-use, anonymous or forwardable auto-join. A stolen claimant can consume an invite but cannot gain access; owner revokes/reissues. |
| **T4 — households** | Owner assigns one authenticated responding account per household; that account may use up to three sessions/devices. Household identity is a service record, never a display name or claimed household_id. Owner assignment changes invalidate the old assignment epoch before new responses. One accepted response per household/round/version; concurrent replacements conflict visibly. Owner may resolve identity disputes and invalidate a disputed response with a reason, but cannot fabricate another household's answer. The assigned respondent must submit the replacement. Portable label-only replies remain untrusted local imports and never become authenticated room votes automatically. No proxy-response delegation. |
| **T5 — recovery** | Use an authenticated account with a separately verified account-recovery mechanism; anonymous device identity cannot own a room. An existing owner may transfer ownership to a current member only through explicit confirmation by both authenticated accounts, each freshly authenticated within five minutes, with atomic single-owner replacement. **No automatic successor, majority takeover, support override, old-invite recovery or display-name recovery.** Credential reset restores the same authenticated subject only if the chosen identity provider proves that binding. If all owner credentials/recovery routes are lost, administration stays unavailable; existing members keep only their current permissions and their already-retained copies. A locally held authorized backup may start a new independent room, never seize the old one. |
| **T6 — disclosure** | Publish only a fresh explicit allowlist described below, with an owner preview of fields/media before initial publication or widening. Exclude booking fields, sourceText, travelerNote, group ledgers/ballots/workspace, live lineage, revision/applied maps and deleted/private history. Responses have a separate household-authorized endpoint; no raw reply payloads in the ordinary board feed. Narrowing/deletion stops future server reads and references; downloaded copies cannot be recalled. Existing unknown/restricted art requires credit; no new rights/license policy. |
| **T7 — concurrency/Undo** | Use server-assigned versions and an atomic accepted-operation receipt. In v1, **all writes to the same entity require its current base version**; different entities may commute. No field-level or text CRDT merge. Move/resize are whole geometry changes; stale edit/replace/delete/scope/response/round operations reject visibly with recoverable local drafts. Response acceptance also requires current open-round and household-assignment epochs. Close-round and response acceptance serialize at the trusted boundary. Undo is a new precondition-checked operation for the initiator; never replay another person's local Undo stack or erase their later accepted edit. Lost acknowledgements retry the same operation ID and return the same receipt, not a second effect. |
| **T8 — limits/retention** | Approve the **provisional numeric ceiling table** below for proof fixtures, not as measured capacity or provider quotas. Free shared rooms remain free; limit failures preserve local drafts and offer export/retry. No paid upgrade prompt or automatic room expiry. Security revocation, withdrawal of shared content and owner-requested deletion must remain available at every quota. |
| **T9 — local privacy/lifecycle** | Default remote room content to session-memory caching. Before logout with unsynced work, offer an explicit local backup or discard choice; do not silently lose drafts. Persistent offline copies require an explicit “Keep on this device” choice stating that the OS/browser user can read that copy after logout. Label retained copies with account/room; labels and hidden UI are **not encryption**. Existing standalone private local boards stay local and unchanged, never implicitly uploaded by login/join. Logout/account/room switch stops subscriptions and invalidates the initiating identity/room generation for pending work; precommit uploads are cancelled/quarantined and never rebound to the next account. Clear room cache/object URLs on logout; explicitly retained downloads cannot be recalled. |
| **T10 — versions** | Support **one writable shared schema major** at a time. Every operation declares schema/capability and server entity version. Unsupported versions reject before writes; unknown fields reject. Do not send newer private/unknown fields to an old reader. A room migration requires owner acceptance of a preview, a compatible backup, a separate validated copy, durable reopen and only then pointer publication; original remains retained until verified. Offline old clients keep local drafts and must update/reconcile before resubmission. No assumed 30-day dual-write compatibility or silent downgrade. |

## Provisional ceilings for T8

These numbers are **unmeasured owner proposals**. They are not verified Firebase capacities, throughput, costs, mobile-memory acceptance or a promise that every maximum combination fits a device. Implementation must test each limit and limit+1, simultaneous boundaries, fan-out and actual serialized bytes before release. Changing them requires a recorded owner decision; never relax existing package/test limits to pass.

| Resource | Proposed ceiling and behavior |
| --- | --- |
| Rooms/accounts | 3 owned rooms and 10 joined rooms per authenticated account; 16 active members and 8 households per room; 3 active sessions per account per room. |
| Content | 500 active shared cards/presentations combined; 200 referenced media objects; 50 MiB total shareable snapshot budget **including metadata and media**, with 10 MiB maximum per portable file. Existing native package limits remain unchanged and every export must independently fit them. |
| Operations | 64 KiB serialized intent, 1 logical entity operation per request, 100 pending operations or 1 MiB pending serialized work per local account/room (whichever first). Excess remains local unsent draft; never discard it. |
| Admission | 60 write attempts/minute/account/room, burst 10; 10 invite-redemption attempts/minute/account and network bucket. These are provisional abuse-control policy targets, not proved provider features. Uniform unauthorized/not-found responses must not reveal room or media existence. |
| Invitations/staging | 16 outstanding invites/room; 24-hour invite expiry. One concurrent media decode per client; one upload per account/room; 2 staged uploads and 20 MiB total staging per account/room. Uncommitted staging expires after 1 hour. Commit rechecks current authorization; staged bytes are readable only by their uploader and service. |
| Media | At most 5 selected files per gesture; 10 MiB/file, 50 MiB/gesture; 8192 pixels/side and 16,777,216 pixels/image, bounded-header check before decode. Shared-room service must independently enforce upload/type/resource bounds; local checks alone do not establish trust. |
| Receipts/history | 20,000 accepted content-operation receipts per room, retained for that room's lifetime with only operation ID, principal, kind, entity/version, request digest and bounded outcome—not prior/private content. At the ceiling the room stops accepting ordinary content writes; it does not prune receipt identity then replay old requests. Export/read/security controls remain available; owner may explicitly create a new room from an authorized current snapshot. No cross-device persistent Undo history promise. |
| Deletion/security controls | Content withdrawal/revocation operates outside ordinary content-write quotas and remains idempotent. Retain at most 1,024 redacted security audit entries for 30 days; authorization uses current membership/epochs, never this expiring log. Withdrawn payloads and unreferenced media stop being served immediately and are deleted from active storage within 24 hours. Backups containing them expire within 30 days; if the selected stack cannot meet these retention targets, release is blocked. Active room content otherwise has no inactivity deletion date. Owner-requested room deletion retains a minimal inaccessible closed-room identifier/epoch fence against replay, not payloads. |

A cap is not an automatic-deletion date for ordinary room content. The one-hour staging TTL and explicit-withdrawal deletion schedule concern uncommitted or deliberately removed data only. Receipt limits deliberately trade indefinite editability for a bounded first implementation; they must be disclosed before room creation.

## Exact projection boundary and data flow

Local private store → explicit publication preview → typed intent → authenticated room service → current membership/role/household and precondition checks → **one atomic acceptance plus receipt** → authorized shared read projection. Server-accepted shared records are a distinct store; never encode or upload the live local Y.Doc. Shared downloads do not become instructions.

Allowed room metadata: title, city/cityId/countryCode, timeZone, dates and board kind. Allowed card payload: shared ID, kind, title, body, stage, status, day/time, placeId/location, provenance, approved public source citation (provider/id/canonical URL/date/version), referenced shared asset IDs, x/y and saved board width/height/stack. Allowed presentation payload: shared IDs/references, surface, geometry/crop/rotation/stack/lock and effective shared visibility. Allowed asset payload: room-scoped asset ID/hash, safe MIME/dimensions, caption, credit/rights and approved public source citation. Only server-derived accepted version/timestamp and member author identity may accompany these records. No arbitrary source-object or metadata spread. Other fields deny by default.

Card body/location/caption can themselves contain personal information: explicit publication preview is required; an allowlist is not a semantic guarantee that their contents are public. Private original source excerpts and travelerNote stay local even when a related card is published. Private asset bytes or ancestor references must not enter the room by a shared derivative shortcut. Shared media must have an approved, metadata-sanitized variant and validated room-scoped reference closure; hashes never authorize cross-room retrieval.

Five visible states remain: **in-memory → committed locally → pending server → accepted**, or **rejected/conflicted**. “Committed locally” may be shown only after durable local save; a memory-only draft must remain labeled in-memory. No provider configured/proved means “Shared rooms unavailable,” not simulated acceptance. Server receipt existence is not proof another participant viewed the result.

## Why A, and what remains unproved

| Option | Source-bound judgment |
| --- | --- |
| A — trusted typed-command service | Recommended **contract boundary**, because membership/household/round/media/receipt invariants need one acceptance authority. It permits an explicit narrow validator alongside existing commands instead of raw document mutation. It still requires implementation and atomic storage/identity proof; no current backend is certified. |
| B — direct typed records plus database rules | Not selected for this first contract. No repository evidence proves all cross-record, revocation, round-close and media invariants in a selected rules/transaction system. Fewer service functions alone is not evidence of a smaller *enforceable* solution. Revisit only with equivalent attacker-proof evidence and owner approval. |
| C — membership-gated raw Yjs | Rejected as the sole boundary. Current local Y.Doc contains private/history/group data, and convergence does not validate actor, household or semantic authority. |

Evidence at the pinned source: trip/model.ts defines the combined document; trip/persist.ts encodes it; trip/package.ts constructs a fresh filtered document and applies media/package limits; trip/session.ts accepts a locally supplied Actor and local command guards; trip/revisions.ts derives local numeric revisions; trip/response-ledger.ts explicitly reports household-label identity, not authentication. The inherited OAuth code is a separate connection surface and its Firestore rules deny direct client access; neither proves MoT room identity, recovery or Storage authorization. Hosting is not such proof either.

This packet authorizes **no network/provider verification now**.

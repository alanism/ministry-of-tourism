# MOT-106 local household shortlists

Open the board switcher and choose **Group preferences**. With no declared group, enter one household per line, choose K3 or K5 and select existing shared board cards for a city round. Private cards are excluded. Stable household and round IDs use MOT-105's person-only configuration command; changing the roster or creating later proposals remains available through that contract. A declared round's options and scale cannot be silently changed.

Select a household and round. Numbered rank selectors reorder or clear choices without drag; clearing compacts the remaining ranks. Adding at capacity requires clearing a rank first and never silently drops an option. The scale is shown before responding: K5 gives 5,4,3,2,1 points and K3 gives 3,2,1. Fewer ranks are allowed. Stamps (Approved, Maybe, Denied, or none) and an optional explicitly shared note stay independent. An unranked option is not a dislike; Approved never authorizes a booking, payment or disclosure. Denied marks a participation concern, regardless of preference rank. Feasible scheduling and participation enforcement belong to MOT-110/111.

No local response is different from an empty or partial response. **Respond without ranks** records an empty response; **Remove response** returns to no response. Responses are attributed to stable household IDs; display names do not authenticate anyone. Undo uses the existing actor stack, so the most recent person action (including declaration) is undoable. The existing save indicator describes actual IndexedDB durability.

The optional `meta.groupBallots` stores editable local responses, with one entry per `(proposal_version, round_id, household_id)`. `trip_ballot_update`, `trip_ballot_clear` and `trip_ballot_read` are person-only commands. Unknown identities, foreign options, duplicate/skipped ranks, excessive K, extra fields and oversized notes fail before writes. Metadata is checked again when opening a trip. Public agent reads and metadata command results omit local ballots. Personal ZIPs preserve them; shared guide/stay/selected packages and guest copies omit them, including their encoded document.

These are local editable responses, without an exported response revision or hash. They are not submitted into MOT-107's returned-file ledger or automatically shared. Response-envelope distribution and organizer collection remain separate work; no new clock-based ordering or duplicate voter is introduced here. Tallying remains MOT-108. Source cards, the itinerary and saved source snapshots are untouched.

Regression coverage: `group-ballot.test.ts` and `RankBallot.test.ts`. Builder evidence, including RED runs, actual browser input, native persistence, offline personal import after preload and 1440/768/375/280 screenshots, is retained in the canonical planning folder under `Design Sprints/Build-MOT-106-2026-10-30`. Browser plugin was absent, so validation used sandboxed Playwright Chromium. Physical devices and independent design review remain unverified. No PDF work, model calls or deployment.

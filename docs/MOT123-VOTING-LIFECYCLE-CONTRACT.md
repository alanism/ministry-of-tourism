## 1. Approved policy, unchanged arithmetic

Use only `mot-household-sticker-points@1`: one household has one response; K is 3 or 5; rank r earns `K + 1 - r`; unranked options earn zero; unused points are not redistributed. Contiguous unique partial rankings and an explicitly submitted empty ranking are valid. Empty is zero ranked points, not “no valid response”; absent, unresolved and conflicting responses remain distinct. No transfer/elimination/exhaustion algorithm exists under this selected policy. Ties remain tied; option-ID display ordering never selects a winner.

Destination totals identify advisory leaders; no destination is automatically selected. City/activity totals provide an advisory shortlist without a seat count or automatic itinerary insertion. Closing fixes a tally, not unanimity, consent, a booking or a purchase. Rankings never add/remove Approved/Maybe/Denied stamps; a high score cannot override Denied or confirmed feasibility constraints. Do not silently strike an option, renumber remaining ranks or substitute the next option because of a stamp.

The organizer is the existing local human actor, not a newly authenticated remote role. Person-only commands and explicit sender-label resolution remain. Hashes, files, roster labels and a local actor name confer no room membership/household authority. MOT-130 still owns remote authorization.

## 2. Source facts and smallest extension

Current `group-preferences.ts` has strict version-1 immutable round definitions and K3/K5 weighting. `preference-tally.ts` already computes the approved policy correctly, but returns the method in its output rather than storing an explicit lifecycle declaration. `response-ledger.ts` chooses highest **resolved** revision per household; equal-highest distinct responses conflict and count neither. Its active proposal is the **global maximum** proposal version. `group-workspace.ts` validates asynchronously and commits through a one-use document/revision-bound prepared receipt. Existing generic Undo covers trip metadata; outbound response caches in `tripClock` are outside Undo.

Preserve those pure legacy inputs, outputs, schemas, strict unknown-field checks and current tests. Do not make every existing fixture acquire a lifecycle or relax an assertion. Trips/rounds with no new declaration remain labelled **legacy positional round; no recorded open/close lifecycle**. Do not invent historical open/close events or retrospective owner consent. New app-created managed rounds must store/show the declaration before entry. Moving a legacy round into the managed workflow starts a fresh round/proposal; old responses stay historical and are not auto-submitted.

Recommended narrow paths: optional versioned lifecycle metadata within the existing private `groupWorkspace` (method/declaration and draft/open state), human-only declare/open/prepare-close/commit-close commands, and—if §5 option A is approved—an authoritative closed record under a dedicated `tripClock` prefix, analogous to existing durable response identities. This reuses the current group/ledger/session/package paths; it is not a second voting engine. Do not change group contract version 1 into a new accepted version merely to bypass existing version-rejection tests.

Each declaration binds stable `trip_id`, `proposal_version`, `round_id`, round kind/city, options/K/weighting, supported method ID/version, advisory purpose and the eligible household-ID roster. Display names may change without changing identity. Unsupported method/weight values are rejected, not defaulted. Keep existing bounds (100 households/100 rounds/200 options/1000 ledger entries and frozen package caps); fail explicitly when another version cannot fit.

## 3. Managed state transitions

- **Draft:** declaration visible; no submitted/accepted-vote claim. A local ranking may be a clearly marked draft, but no active response export/counting before explicit Open. A file received before opening is history/data, not an accepted counted response; opening must not silently promote unreviewed imports.
- **Open:** human explicitly opens the declared round. Show method/version, K, provisional totals and pending/partial/conflict/needs-resolution coverage. Existing hash, revision and sender-resolution rules determine the provisional counted set. Unresolved newer delivery does not erase an older resolved current response; the unresolved warning remains visible.
- **Closed:** human explicitly confirms a displayed close preview. Freeze the exact counted responses and complete result/coverage at that boundary. Show when/how it closed and the excluded/pending/conflict facts; no automatic closure timer or minimum quorum is introduced.
- **New round/proposal:** reopening or changing options, K, weighting or method creates a new identity. Preserve all prior definitions/ballots/seals. Start with no accepted responses and no preselected old consent; the household supplies a new explicit response. Only the selected method/weight is implemented, so choosing another method/weight remains unsupported rather than silently available.

Existing global latest-proposal behavior stays explicit: advancing `proposal_version` makes all earlier-version rounds historical in existing pure tally/planning APIs. The UI must preview that scope before confirmation, not pretend it reopens only one city while other old rounds remain current. For this slice, new managed proposal versions start from explicitly selected round definitions/roster and require fresh responses; do not change the legacy global-current algorithm or silently clone votes. Closed historical results remain viewable through their sealed result path even when the pure current-tally API correctly refuses the old proposal.

## 4. Close snapshot and late arrivals

Prepare Close from one captured document instance, board revision, configuration/declaration digest, eligible roster and ledger/resolution snapshot. Cryptographically validate all selected response bodies before creating a one-use prepared receipt. Recheck those identities synchronously at commit; no await or fallible per-record writes after the first committed write. Actor/context change, navigation, cancellation, revision change, a second close or changed resolution invalidates the pending receipt. An existing receipt for import/export/planning cannot land stale work after Close.

The final record must contain enough immutable data to verify and show its result independently of future mutable metadata: trip/round/declaration/method and roster snapshot; accepted `response_id`s **and canonical response bodies**; excluded/conflict/unresolved identifiers and frozen coverage; canonical final tally and its content digest; close event identity and informational time/local actor. Recompute/validate consistency at load/import, rather than trusting a caller-supplied tally. IDs alone are insufficient because Undo can remove ledger entries and roster edits can change coverage. Response timestamps remain informational, not eligibility ordering.

Late valid returns and later sender resolution may be retained in the bounded ledger as **uncounted after close**. They must never change the closed totals, stamps, notes, constraints or coverage. Byte-identical duplicate deliveries remain idempotent. Invalid hashes/unknown options/wrong identities reject atomically. If history is full, refuse with existing backup/new-round guidance; do not silently discard history or enlarge the limit.

Every document-bound consumer must distinguish provisional/live data from sealed results. In particular organizer UI, plan preparation/Apply, feasibility, routing and adaptation must not relabel a mutable `mergeResponseLedger.current` result as the closed result. Use one small resolved-round selector for these callers, or explicitly refuse unsupported managed-round operations. Pure tools over explicitly supplied legacy configuration/ledger remain read-only calculations and do not acquire private board reads or imply a saved closure. Later Denied information cannot be treated as permission to attend merely because it was uncounted; show the late concern and require explicit reviewed planning/fresh-round action, never silently amend the sealed result or assume consent.

## 5. Remaining owner fork: Close versus generic Undo

The approved rule “reopening creates a new round/proposal” rules out Undo reopening the **same** closed identity. It does not specify which user-facing Undo behavior to provide. Existing `TripSession.undo` can restore previous metadata while `tripClock` survives; simply adding `closed: true` to metadata cannot meet the freeze promise.

**A — Recommended: durable Close, ordinary Undo cannot reverse it.** Close creates a sealed result outside ordinary Undo. Explain before confirmation: “Closed results are retained. Start a new round to revise.” Do not clear the person's Undo stack. Unrelated edits and legacy/local draft operations remain undoable as before. Undo of an earlier configuration or ledger may remove its live entry, but the self-contained seal stays readable as historical and guards that identity. A reused `(trip_id, proposal_version, round_id)` cannot remove/reinterpret it; reintroduced matching configuration stays closed. New proposal allocation must exceed relevant recorded/closed proposal versions even if current configuration was undone. Import/native recovery preserves and validates these seals. Existing generic Undo is not advertised as undoing Close.

**B — Alternative: explicit “Undo closing” starts a fresh round.** It preserves the original seal and invokes the same explicit new-proposal path with empty responses; it never reopens the prior identity. This requires additional UI and equivalent global-proposal-impact disclosure. It is not ordinary metadata Undo and must not pretend earlier households resubmitted.

**Owner selection: pending.** Neither clearing the Undo history nor silently deleting/reusing the closed identity is an acceptable third option. Until the actual choice is recorded, do not implement finalization semantics by guessing.

Unsupported lifecycle versions, forged computed totals and mismatched record keys must fail before durable writes. Do not drop unknown seal data and report a normal open round.
- New managed private packages need an explicit recognized lifecycle marker in their readable/document contract so clients lacking lifecycle support reject rather than silently export a reopened round. Keep ordinary legacy packages unchanged; no global schema/version bump or test-expectation change is authorized merely for this slice. Establish the supported-version boundary before implementation is called ready. Raw older clients that cannot honor seals are not supported managed-round clients.
- Closing must invalidate freshness even if only clock data changes: existing revision snapshots do not include arbitrary clock fields. Include the selected lifecycle/close state in the relevant prepared-operation guard and revision tracking without making the revision counter depend on itself. Preserve current export-cache concurrent-revision checks.
- The close receipt records a document change, not device persistence or remote sync. Keep current `whenSaved`/tab-only recovery states and do not fabricate server acknowledgements. Room authority remains unimplemented here.

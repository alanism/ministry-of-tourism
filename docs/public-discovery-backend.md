## Authentication and client contract

`GET /api/muse/discovery-status` is a configured-readiness hint (`transport: firebase-attested`, `readiness: configured-only`). It performs no Firestore reads. Available status does not promise remaining quota. Every POST performs durable admission.

`POST /api/muse/discover` requires the exact allowed Hosting origin, JSON at most 2,048 bytes, `x-mot-request: 1`, a verified anonymous Firebase Auth ID token, and a fresh limited-use App Check token. The server validates the full body/schema and byte bound first, then consumes App Check (`consume: true`) and rejects replay, missing consumption confirmation and wrong app IDs **before** the remote Auth revocation lookup. Auth revocation checking and anonymous-only access remain required. A disconnect or the eight-second verification deadline prevents later stages from starting. App Check verification/consumption can itself require remote work; rejected requests are not claimed cost-free. Origins are fixed to the site's `.web.app` and `.firebaseapp.com` URLs. Custom domains and preview domains require reviewed code changes.

The sole accepted body is `{ cityId, seedIds, category, requestId, contributorConsent: true }`; `requestId` is a fresh UUID, and one to three public seed IDs are required. Unknown fields are rejected. Auth identity and App Check tokens are never sent to Meta.

The browser adapter is copied into `apps/web/src/trip/attested-discovery.ts` by the app workstream. Firebase SDK imports are lazy and follow explicit Contributor consent. Persistent anonymous Auth reuses the browser identity after reload; persistence failure prevents discovery. This is a per-browser-identity allowance, not a per-person limit: clearing storage can reset an identity, while the global limits remain shared. Each POST obtains a new limited-use token. `/__/firebase/init.json` supplies public Firebase SDK configuration; it is not a Meta credential.

`apps/web/public/discovery-public.json` now contains enabled public routing metadata for web app `1:944001311456:web:855aefe5cb45c3c2ef6685`. It contains no Meta credential. The matching server flags are enabled through deployment environment configuration. The app dispatches only `firebase-attested` status to the new adapter and retains legacy loopback support. The source-only `backend/discovery/client` scratch handoff is excluded from integration and deployment.

## Durable admission and bounded provider work

Firestore transactions atomically reserve an attempt before any FCC or Meta call. They coordinate all service instances using a global control document, UTC day counters, salted HMAC identity/day counters, and UUID request records with private completion nonces. They never store raw UID, tokens, private content, provider keys, prompts or generated venue text. Attempts are not refunded. Completion is idempotent. Request replay remains rejected after a process restart.

- 100 lifetime attempts; 20 attempts per UTC day; three per persistent anonymous identity per UTC day.
- Two durable concurrent leases; leases expire after 75 seconds.
- Expired uncertain leases or missing/invalid provider usage halt further admission for owner review. Failed completion leaves its durable lease; it is not silently retried or refunded.
- Cancellation before provider dispatch prevents paid work; an admitted attempt remains burned with known zero provider usage. Once provider dispatch may have incurred usage, the handler continues to await that single request within its existing 30-second deadline after a client Stop/disconnect, records the actual usage, and returns a cancelled result without candidates. There is no detached background task, retry, refund, automatic Add or late UI update. A normal disconnect with known usage therefore does not halt the global preview. A genuine provider timeout, missing usage or accounting failure remains uncertain and conservatively halts admission (immediately or when its durable lease expires).
- 30-second provider timeout; no provider retry; at most two web-search tool calls; 2,500 output tokens including reasoning; 12,000-byte public input; 192,000-byte response bound.
- 200,000 observed input-plus-output tokens is an **after-response circuit threshold**, with output headroom checked at admission. Search/input usage is variable and concurrent in-flight work may overshoot. This is **not a hard total token or dollar ceiling**. Cloud/Auth/App Check/Firestore costs are separate. A hard financial cap is not claimed.

Function deployment bounds are two instances, concurrency four per instance, 256 MiB and a 60-second request timeout. Durable leases impose the lower shared provider concurrency. The 30-second provider deadline does not include the final awaited usage transaction; an interrupted/failed accounting transaction retains the lease and conservatively halts later admission on expiry. No late response is sent to a disconnected client, including a disconnect during accounting. Invalid origin/body/token requests do not enter the ledger; token verification and platform requests can still incur platform costs. Status polling does not read the ledger. Internet-facing infrastructure cannot promise zero-cost abuse resistance.

Only fixed public FCC feed content is sent to Contributor. The UI must retain the Contributor disclosure: public inputs are shared with Meta and may improve its models; personal, sensitive or confidential content must not be submitted. This does not change existing photo/private-board privacy controls. Public discovery cannot be reused to judge private photos.

## Additional durable attestation replay guard

A live, nonpaid check observed the same limited-use App Check token reaching admission twice with distinct request UUIDs, despite SDK `consume: true`. No Meta call occurred: both requests deliberately used a nonexistent FCC seed and recorded zero provider usage. The release therefore also requires the signed token's unique `jti` claim and hashes it with the verified app ID. Only that irreversible fingerprint is passed to the ledger. Missing/malformed unique IDs fail before Auth lookup. The existing admission transaction atomically rejects an existing `motDiscoveryAttestations/<hash>` record and creates a marker only when a new attempt is admitted, alongside its request/counters/lease. The client request UUID replay guard remains intact. This adds at most one marker per admitted attempt, bounded by the same 100-attempt lifetime cap, without storing the token or changing counters/salts. SDK-reported replays still reject before Auth; the independent durable guard rejects any remaining reuse before provider work.

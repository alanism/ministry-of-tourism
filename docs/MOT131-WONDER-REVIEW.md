## Blocking finding

### [P1] Specify the refusal recovery workflow before calling the contract implementation-ready

**Contract location:** `docs/MOT131-BOARD-GEOMETRY-PROPOSAL.md:397` (authoritative G6), together with §9 at lines 292–300; corresponding G6 in `MOT131-G1-G6-OWNER-REVIEW.md`.

**Reason:** G6 correctly requires an original backup, compatible read-only legacy inspection/export and a previewed, explicitly accepted repair. It expressly says the repair workflow must be specified before migration is ready, but no actual workflow is specified. This is a reachable compatibility failure, not merely a missing future test: v2 accepts every finite card x/y, whereas v3 would refuse negative positions and positions whose default 1200 × 900 footprint overflows. `persist.ts:14–32` destroys the attempted document on failure; its `original` return is available only after success. `trip-store.ts:60–71` propagates that failure before obtaining an open trip. The ordinary model readers and `package.ts:28–42` validate against the current schema, so after the bump they cannot automatically provide inspection/export of a refused legacy trip. Preserving bytes in an undiscovered store alone does not fulfill the approved recovery promise.

Without clarification, an implementer must invent whether recovery uses an older build, an in-app legacy reader, an automatic layout transform or manual edits, and when a repaired copy becomes authoritative. Those choices affect accessibility, data integrity and the refusal guarantee.

**Minimal proposed correction:** add a short normative recovery subsection covering the following behavior. This elaborates the already approved G6 instead of choosing a new layout policy:

1. Discover and identify the selected original store/package before migration. Preserve its bytes and identity without opening it for writing. Distinguish absent storage from present-but-invalid or unreadable storage; the latter enters recovery and must not silently select an older snapshot. A corrupt newer candidate may be exposed for backup alongside older candidates clearly labelled as older, without automatically adopting one.
2. On a geometry-only refusal of an otherwise valid supported v1/v2 document, open a local, read-only legacy inspector using version-appropriate validation. Show the original cards, stages, coordinates and source/private content under the same local owner access; show offending IDs and violated bounds. Do not route the original through v3 readers or change its schema marker merely to display it. Unknown/future or corrupt documents get an error and original-byte backup, not guessed interpretation or layout repair.
3. Make the original imported package downloadable unchanged. For a stored trip, expose the untouched legacy document snapshot and available original referenced media, plus a compatible legacy native export when it satisfies the existing package limits. Explicitly report missing media and over-budget exports. A raw document backup is not advertised as a complete media package; do not increase 10 MiB/file or 50 MiB/package limits to make recovery appear successful. The untouched source store remains retained.
4. Provide a separate in-memory repair draft for geometry-only failures. The person supplies replacement x/y for the offending cards; the UI previews old and proposed rectangles and lists exactly which coordinates will change. All retained content, IDs, stage/day/time, scope, provenance, assets and legacy magazine records remain unchanged. No automatic clamp, reordering or offset flip. Defaults apply as approved. Explicit acceptance authorizes only that displayed coordinate repair; cancel/navigation/stale source invalidates the draft without writes.
5. Revalidate the complete accepted draft before writing a separate v3 copy. Do not overwrite the original or merge an interrupted/corrupt v3 candidate into the repair. Publish the copy as usable only after durable save and successful reopen/validation; failure leaves the original and recovery route available. A retry must not silently bless an existing failed candidate. Normal migration retains the original too, at least until the same durable-save/reopen condition is met.
6. Require evidence for refusal → original backup → legacy inspection/export → preview → cancel/accept → durable reopen, including missing media, over-budget backup, failed save and interrupted retry. This evidence is downstream implementation work, not something this documentation review can claim.

Manual coordinate replacement is a minimal proposed realization of the already approved explicit repair, not a new automatic placement rule. If the product instead wants automatic arrangement, silent fallback to an older copy, transformed backup bytes or a different repair authority, that would need a separate owner decision. The parent can reconcile the proposed narrow workflow locally and return the amended contract for re-review.
